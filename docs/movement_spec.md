## Контракт `Pathfinder`

```text
FindReachable(
    start,                  // GridPosition
    actionPointBudget,      // int, >= 0   (0 валиден: вернёт только start)
    movement,               // int, > 0
    mover,                  // идентификатор движущегося юнита
    movementContext         // battle-owned reference type: карта, occupancy, отношения
)
```

Предусловия `movement > 0` и `actionPointBudget >= 0` проверяются **один раз на границе
запроса**, до касания рабочих массивов. Нарушение → `ArgumentOutOfRangeException`, а не
деление на ноль и не частично изменённое состояние.

Неизменны в течение одного запроса: `mover`, `start`, карта, occupancy, отношения
`Self`/`Ally`/`Enemy`, `movement`, `actionPointBudget`.

`movementContext` живёт столько же, сколько бой, передаётся ссылкой, не создаётся на
запрос (Zero-GC). `Pathfinder` **не** хранит `movement` как состояние экземпляра и **не**
получает `Hero`/`HeroStats`.

### Предикаты

```text
movementContext.CanTraverse(from, to, mover)   // получает mover: различает Self/Ally/Enemy
movementContext.CanStopAt(cell)                // без mover, не знает про start
```

Оба детерминированы, без побочных эффектов, без аллокаций на вызов.

### Результат — три метода с разными областями определения

| Метод | Что отдаёт |
|---|---|
| `TryGetCost(cell, out cost)` | любая клетка, достигнутая как transit-valid в пределах бюджета — включая start и **клетки союзников** |
| `CopyReachableTo(buffer)` | только допустимые конечные: start + достигнутые stop-valid. Клетка союзника **не** попадает |
| `CopyPathTo(target, buffer)` | принимает только start или достигнутую stop-valid клетку. Сам путь при этом **может** содержать промежуточные stop-invalid клетки |

## Алгоритм

| Аспект | Решение |
|---|---|
| Алгоритм | bounded Dijkstra, отсечение по бюджету **до** релаксации: `if (newCost > budget) continue;` |
| Структура приоритета | предвыделенный compact open-set |
| Выбор минимума | линейный поиск **только среди открытых клеток**, не по всей карте |
| Тай-брейк | `(cost, cellIndex)` — полный порядок, не зависит от порядка вставки и от перестановок при swap-remove |
| Релаксация | предшественник меняется только при `newCost < cost[neighbor]` — **строго меньше** |
| Хранение | плоские массивы, `index = y * width + x` |
| Аллокации на запрос | 0 |
| Владение | экземпляр принадлежит конкретному бою, **не** static |

Рабочие массивы: `cost[]` (int), `predecessor[]` (int), `state[]` (byte:
`NotSeen`/`InQueue`/`Finalized`), `openList[]` (int), `openCount` (int).

**Инвариант Дейкстры:** клетка со `state == Finalized` при неотрицательных весах не
улучшается никогда. Обязателен тест на это.

**Ловушка индексации:** границы проверяются по `x` и `y` **раздельно**. Одной проверки
`index < cellCount` недостаточно — шаг на восток при `x = width - 1` даёт валидный индекс
в следующей строке.

## Стоимость

Базовые веса (только они лежат в статической таблице направлений):

```text
ортогональный шаг = 10
диагональный шаг  = 14        // ×10 от 1 и √2≈1.414, ради целочисленности
```

Фактическая цена **каждого ребра** для конкретного юнита:

```text
stepCost = ceil(baseStepCost * 100 / Movement)

// целочисленная безопасная форма:
scaledCost = baseStepCost * 100                       // максимум 1400, влезает в int
stepCost   = scaledCost / Movement
           + (scaledCost % Movement == 0 ? 0 : 1)
```

`Movement = 100` — нейтраль, даёт ровно `10`/`14`. Инвариант `Movement > 0`;
`Movement <= 0` — ошибка создания характеристик, а не «обездвижен» (обездвиживание —
будущее отдельное состояние `CanMove = false`).

`pathCost = sum(stepCost(edge))`. Фактический `stepCost` используется **и** при
релаксации, **и** при отсечении по бюджету.

❗ **Нельзя** построить путь по базовым `10/14`, а потом отмасштабировать итог: округление
поединочное, и при разных `Movement` оптимальный маршрут разный. Проверочный пример —
две дороги из `(0,0)` в `(10,0)`, 14 ортогональных рёбер против 10 диагональных
(при базе обе = 140):

| `Movement` | орто-шаг | 14 рёбер | диаг-шаг | 10 рёбер | Победитель |
|---|---|---|---|---|---|
| 60 | 17 | **238** | 24 | 240 | ортогональный |
| 80 | 13 | 182 | 18 | **180** | диагональный |
| 100 | 10 | **140** | 14 | **140** | ничья (проверяет строгую релаксацию) |

## Легальность клетки

| Состояние клетки | Transit | `CanStopAt` | В `CopyReachableTo` |
|---|:---:|:---:|:---:|
| Вне карты | ✗ | ✗ | ✗ |
| Непроходимая местность | ✗ | ✗ | ✗ |
| Пустая проходимая | ✓ | ✓ | ✓ если достигнута |
| С визуальным телом погибшего | ✓ | ✓ | ✓ если достигнута |
| Занята **союзником** | ✓ | ✗ | ✗ |
| Занята **врагом** | ✗ | ✗ | ✗ |
| Собственная стартовая | ✓ | ✗ | ✓ **всегда**, cost `0` |

```text
transit-valid:  в границах && terrain walkable && occupant ∈ { None, Self, Ally }
stop-valid:     в границах && terrain walkable && occupant == None
```

**Инвариант occupancy:** не более одного **живого** юнита на клетку. Проверяется на каждой
границе, меняющей occupancy — при инициализации боя, размещении юнита, перед и после
`MoveCommand`. `Pathfinder` вправе считать состояние валидным и не чинит его.

**start — специальный узел результата.** Публикуется со стоимостью `0` **независимо от**
`CanStopAt(start)`. Исключение живёт в сборке результата, **никогда внутри предиката** —
`CanStopAt` не должен знать про конкретный запрос.

❗ **Нельзя** выбрасывать клетку из графа Dijkstra потому, что `CanStopAt == false`.
`CanStopAt` фильтрует конечные позиции, а не граф поиска — иначе клетка за союзником
станет недостижимой.

## Диагональ

```text
from = (x, y),  to = (x + dx, y + dy),  abs(dx) == abs(dy) == 1

sideA = (x + dx, y)
sideB = (x, y + dy)

разрешено ⟺ IsTransitValid(to) && IsTransitValid(sideA) && IsTransitValid(sideB)
```

**Обе** боковые, и именно **transit**-validity (не stop — иначе союзники блокировали бы
диагональ, хотя сквозь них ходить можно). Варианта «достаточно одной стороны» нет.

Геометрическое следствие (намеренное, это **не** система зон контроля):

- **ортогонально** соседний враг отнимает **3** направления из 8: свою клетку + две
  диагонали, для которых он боковой;
- **диагонально** соседний враг отнимает **1**: только свою клетку.

## AP и выполнение хода

```text
начало боя:        CurrentActionPoints = StartingActionPoints
следующие ходы:    CurrentActionPoints = min(Current + ActionPointsPerTurn, MaxActionPoints)
```

Первый ход **не** получает `ActionPointsPerTurn` поверх стартовых. Неиспользованный
остаток переносится, единственный предел — `MaxActionPoints`. `ActionPointsPerTurn = 0`
валиден. AP — **одна валюта** на движение, атаки, способности и предметы; отдельных
Movement Points нет.

Ход завершается **только** явным `EndTurn`. Ни `0 AP`, ни любое действие ход не
завершают.

Движение разрешено при `pathCost <= CurrentActionPoints`, иначе отклоняется **целиком**:
позиция не меняется, AP не списываются, состояние боя не меняется. Частичного прохода до
последней доступной клетки нет. При `pathCost == CurrentActionPoints` движение проходит
полностью, AP становятся `0`, ход **не** завершается.

Успешный `MoveCommand` **атомарен**: списание полной стоимости и установка конечной
позиции — одной операцией, невозможно одно без другого. Промежуточные клетки доменную
occupancy не получают и не резервируются. Отменить, прервать или вернуть AP нельзя.
Unity-анимация проигрывает уже принятое решение и правилами боя не управляет.

Игрок выбирает **только конечную клетку** — waypoint'ов нет. Preview показывает путь,
полную стоимость и остаток AP, состояние не меняет и AP не тратит. Любая успешная
команда, меняющая AP, позиции или входы `CanTraverse`/`CanStopAt`, **инвалидирует**
рассчитанную зону — перед следующим preview она считается заново.

`AttackCommand` **никогда** не перемещает персонажа: цель вне дальности → атака
отклонена, AP не списаны, позиция та же.

## Не решено — ждёт своего ADR

| Вопрос | Куда |
|---|---|
| Линия видимости, укрытия, дальность атак, касание углов | ADR-0004 |
| DTO команд, связь preview↔execution, snapshot/version, повторная валидация, результат `MoveCommand` при цели = `start` (no-op) | ADR-0005 |
| Порядок обработки команд, детерминизм между средами | ADR-0006 |
| Что шлёт клиент и что перепроверяет хост | ADR-0007 |
| Таймер хода и AFK в коопе | до конца сетевого этапа |
| Конкретные балансные числа AP, атак, способностей | вне ADR (данные) |

Вне скоупа MVP: юниты крупнее клетки, полёт/прыжок/телепорт, принудительное перемещение,
обмен позициями, толкание, одновременное движение нескольких юнитов, зоны контроля и
атаки по возможности, ловушки и события на промежуточных клетках, тела как препятствия,
terrain-множители и поверхности, модификаторы `Movement` от экипировки и баффов.
