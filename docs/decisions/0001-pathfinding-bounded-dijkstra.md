# ADR-0001: Bounded Dijkstra с предвыделенным compact open-set для перемещения по сетке

- **Статус:** Accepted (решение зафиксировано; реализация не начата — см. `docs/roadmap.md`, Веха 1)
- **Дата:** 2026-08-04
- **Затронутые файлы (будущие):** `Assets/Scripts/Core/Combat/GridPosition.cs`, `Assets/Scripts/Core/Combat/Pathfinder.cs`
- **Проверено:** два независимых враждебных ревью (разные модели), 14 утверждений проверены построчно, обе выявили по одной реальной ошибке в предыдущей версии решения — см. «История пересмотра» внизу.

## Контекст

Пошаговая тактическая RPG, соло-разработка, C# изучается по ходу. Цель — кооп на 3 игроков через Netcode for GameObjects, server-authoritative. Масштаб одного боя: 3 героя + 2–3 врага, карта ориентировочно 30×30, зона досягаемости пересчитывается на старте хода и по клику — не каждый кадр.

Жёсткие ограничения: домен без `UnityEngine`; целочисленные координаты (детерминизм); Zero-GC в боевых итерациях (без лямбд в горячем пути, без аллокаций на запрос); потолок API — `netstandard2.1`, проверяется отдельным compile-only проектом, поскольку Unity на машине разработчика не установлена.

Зафиксированная модель сетки: 8 направлений, ортогональный шаг = 10, диагональный = 14 (масштаб ×10 от 1 и √2≈1.414 для целочисленности). Нельзя срезать диагональ через заблокированный угол.

## Решение

```
Алгоритм:              bounded Dijkstra (ограниченная по бюджету)
Структура приоритета:  предвыделенный compact open-set
Выбор минимума:        линейный поиск ТОЛЬКО среди открытых клеток (не по всей карте)
Тай-брейк:             (1) меньшая cost, затем (2) меньший cellIndex — полный порядок,
                       не зависит от порядка вставки/перестановок при swap-remove
Релаксация:            предшественник меняется только при newCost < cost[neighbor]
                       (строго меньше; равенство не переписывает предшественника)
Координаты наружу:     readonly struct GridPosition, IEquatable<GridPosition>
Внутреннее хранение:   плоские массивы, index = y * width + x
Аллокации на запрос:   0
Владение pathfinder:   экземпляр, принадлежащий конкретному бою (НЕ static)
```

Внутренние структуры:

```
cost[cellIndex]         int    — минимальная известная накопленная стоимость
predecessor[cellIndex]  int    — предшественник для восстановления пути
state[cellIndex]        byte   — NotSeen = 0 / InQueue / Finalized
openList[]              int    — компактный массив индексов открытых клеток
openCount               int    — сколько элементов реально занято
```

Ключевые инварианты:

- Отсечение по бюджету — **до** релаксации: `if (newCost > budget) continue;`.
- Финализированная клетка (`state == Finalized`) при неотрицательных весах не улучшается никогда — инвариант Дейкстры, обязателен тест на него.
- Проходимость ребра и возможность остановки — **два разных предиката**, не один: `CanTraverse(from, to)` для прохода через клетку (нужно для союзников/врагов, через которых можно пройти, но нельзя закончить движение) и `CanStopAt(cell)` для того, что показывается как зона досягаемости в UI.
- Индексация `y * width + x` проверяется границами по `x` и `y` отдельно при обходе соседей — проверка одного `index < cellCount` не ловит заворот через край карты (шаг на восток с `x = width - 1` даёт валидный индекс в следующей строке).

## Отвергнутые альтернативы

| Вариант | Почему отвергнут |
|---|---|
| **BFS** | Упорядочивает обход по числу шагов, а не по стоимости; при весах 10/14 даёт неверный результат уже на сетке 3×2 без единого препятствия. Результат зависит от порядка направлений — минимальный контрпример, не искусственный. |
| **`System.Collections.Generic.PriorityQueue<,>`** | Отсутствует в `netstandard2.1` (появился в .NET 6). Компилируется в тестовом проекте под `net10.0`, падает в реальной Unity API-поверхности. |
| **Bucket queue, односвязный интрузивный список** | При допущении повторных вставок клетки (после улучшения стоимости) `nextInBucket[cell]` может хранить только одну связь — повторная вставка рвёт старую цепочку. Симптом не исключение, а молча уменьшенная зона досягаемости; на маленьких картах тесты могут проходить, несмотря на баг. |
| **Bucket queue, двусвязный список + decrease-key** | Технически корректен, разобран во всех деталях (detach/attach, случай головы ведра, порядок операций при обновлении cost). Отвергнут не из-за корректности, а по соотношению риск/выгода для этого масштаба — см. следующий раздел. |
| **Наивный `O(V²)`, поиск минимума по всей карте** | Сложность зависит от размера карты (900 клеток), а не от бюджета — не подходит независимо от масштаба боя. |
| **SPFA / Bellman-Ford с переоткрытием клеток** | Корректен, но немонотонен (стоимость клетки может улучшиться после того, как её уже обработали) — размывает инвариант «клетка финализируется один раз», на котором держатся тесты. Худший случай `O(V·E)`. |
| **Рукописная бинарная куча** | Корректна, но decrease-key требует sift-операций и карты «клетка → позиция в куче» — исторически один из самых багоёмких кусков pathfinding-кода. Не даёт измеримого выигрыша на масштабе 3+3 юнита. |

## Почему compact open-set, а не bucket queue — решающий аргумент

Зона досягаемости ограничена бюджетом движения, то есть открытый фронт — десятки клеток, не вся карта. При таком масштабе:

- **Decrease-key с open-set бесплатный**: улучшение стоимости — это одна запись `cost[n] = newCost`, клетка никуда не переезжает, потому что порядок нигде не материализован явно.
- **Нет sentinel-дисциплины**: не нужны значения-заглушки для «пустого ведра», не нужен `Array.Fill`.
- **Режим отказа при ошибке — громкий, а не тихий.** Баг в open-set даёт видимо неверный ответ, легко поймать тестом. Баг в двусвязных ведрах (перепутан порядок `oldCost`/`cost[cell]`, забыт случай головы ведра при detach) даёт правдоподобную, но неверную зону — именно такой класс ошибок труднее всего находить человеку, который впервые пишет pathfinding.
- Объём кода — примерно вдвое-втрое меньше (4 массива состояния против 6, ни одной sentinel-проверки).

Это **не** временное упрощение ради обучения — при заявленном масштабе (десятки открытых клеток на запрос, не каждый кадр) compact open-set является асимптотически и практически достаточным окончательным решением, а не заглушкой, которую придётся заменить при росте проекта.

## Триггер пересмотра

Вернуться к bucket queue (круговые ведра, размер `maxEdgeWeight + 1 = 15`, не индексированные по бюджету), если хотя бы одно:

- Запрос должен регулярно охватывать более ~500 открытых клеток за один вызов.
- Профайлер в реальном Unity Editor показывает более 1 мс на запрос зоны досягаемости.

Если триггер сработает — это отдельный ADR, не правка этого файла (см. «Правила ведения» внизу).

## Осознанно НЕ покрыто этим ADR

Следующие решения зависят от геймдизайна, а не от алгоритма, и должны фиксироваться отдельными ADR при принятии:

- **Модель AP/движения**: единая валюта AP=стоимость движения, либо два отдельных пула (Movement Points + Action Points, как в XCOM), либо конверсия с округлением вверх. Влияет на то, какое состояние синхронизируется по сети через `MoveCommand`.
- **Правило диагонали**: обе смежные ортогональные клетки свободны, либо хотя бы одна.
- **Спецификация линии видимости**: thin line vs supercover, поведение на касании угла, симметричность, блокировка юнитами.

## Последствия

**Плюсы:** минимальный риск реализации для разработчика без опыта в pathfinding; детерминизм не зависит от порядка вставки/удаления благодаря полному порядку тай-брейка; путь одинаков между запусками и между Unity/Mono/IL2CPP и тестовым `.NET`, потому что вся арифметика целочисленная.

**Минусы, принятые осознанно:** open-set не является асимптотически оптимальным для больших открытых множеств — приемлемо только благодаря ограниченному бюджету движения. Если бюджет когда-либо перестанет быть маленьким (например, способность телепортации на любую клетку карты без ограничения по AP), этот ADR должен быть пересмотрен явно, а не молча пережит кодом.

## История пересмотра (для доверия к процессу, не трогать при правках выше)

- Первая версия решения (bucket queue, односвязные ведра) проверена ревью №1 — найдена ошибка (У3: односвязные ведра несовместимы с повторными вставками) — решение уточнено до двусвязных ведёр с decrease-key.
- Уточнённая версия проверена ревью №2 (независимая модель) — подтверждены 12 из 14 утверждений, две ошибки исправлены (контрпример BFS на сетке 3×1 геометрически невозможен — исправлено на 3×2; совет «чисти массивы `Array.Clear`» конфликтовал с sentinel `-1` — исправлено на `Array.Fill`) — по итогам сравнения риска реализации выбор пересмотрен в пользу compact open-set вместо ведёр любой конструкции.
- Тай-брейк через «порядок вставки в openList» отвергнут пользователем как некорректный (swap-remove делает позицию в массиве ненаблюдаемой) — заменён на канонический полный порядок `(cost, cellIndex)`.
