# ADR-0002: Единая AP-экономика и стоимость перемещения

- **Статус:** Accepted
- **Дата:** 2026-08-04
- **Связано:** `ADR-0001: Bounded Dijkstra с предвыделенным compact open-set для перемещения по сетке`
- **Затронутые файлы (будущие):** `HeroStats`, `Hero`, логика начала хода, калькулятор стоимости движения, `Pathfinder`, `MoveCommand`, `EndTurnCommand`, UI preview движения, соответствующие тесты и `docs/domain_model.md`
- **Проверено:** внешнее враждебное ревью; замечания по контракту `Pathfinder`, границным тестам, переполнению целочисленной формулы, влиянию `Movement` на максимальный вес ребра и синхронизации документации включены в принятую версию.

## Контекст

Боевая система FantasyRPG должна давать игроку свободу порядка действий в духе первой `Divinity: Original Sin`: в течение своего хода персонаж может несколько раз перемещаться, атаковать, применять способности и предметы, а затем явно завершить ход.

Для движения уже принят ADR-0001: сетка с восемью направлениями, базовая стоимость ортогонального ребра `10`, диагонального — `14`, bounded Dijkstra и детерминированный выбор пути.

Нужно определить:

- какая валюта оплачивает движение и остальные действия;
- как AP выдаются и сохраняются между ходами;
- как характеристика мобильности влияет на стоимость пути;
- что происходит при недостатке AP;
- где проходит граница между доменной операцией и визуальной анимацией;
- как `Movement` конкретного юнита входит в запрос `Pathfinder`, не изменяя принятый в ADR-0001 базовый набор направлений и их базовых цен `10/14`;
- как введение `Movement` влияет на ранее упомянутый в ADR-0001 гипотетический переход к bucket queue.

Цели решения:

- целочисленная и детерминированная арифметика;
- простая server-authoritative валидация в будущем;
- отсутствие скрытого округления и частичного выполнения команд;
- минимальный объём механик для MVP;
- возможность расширения отдельными ADR без усложнения первой реализации.

## Решение

### 1. Одна общая валюта AP

Очки действия — единый ресурс для:

- перемещения;
- обычных атак;
- способностей;
- использования предметов.

Отдельных `Movement Points` нет. Стоимость каждого действия выражается целым числом AP в одной шкале.

Движение использует ту же шкалу, что и ADR-0001:

```text
ортогональный базовый шаг = 10 AP
диагональный базовый шаг  = 14 AP
```

При нейтральном `Movement = 100` фактическая цена ребра совпадает с базовой стоимостью ADR-0001: `10` и `14`.

Точные стоимости атак, способностей и предметов являются балансными данными и этим ADR не задаются.

### 2. Три характеристики AP

`HeroStats` хранит три независимые характеристики:

```text
StartingActionPoints
ActionPointsPerTurn
MaxActionPoints
```

Инварианты:

```text
StartingActionPoints >= 0
ActionPointsPerTurn >= 0
MaxActionPoints > 0
StartingActionPoints <= MaxActionPoints
```

Текущие AP являются изменяемым состоянием `Hero`, а не частью `HeroStats`:

```text
0 <= CurrentActionPoints <= MaxActionPoints
```

### 3. Начало боя и восстановление AP

При начале боя:

```text
CurrentActionPoints = StartingActionPoints
```

Начиная со следующего хода этого персонажа:

```text
CurrentActionPoints = min(
    CurrentActionPoints + ActionPointsPerTurn,
    MaxActionPoints
)
```

Первый ход не получает дополнительное `ActionPointsPerTurn` поверх `StartingActionPoints`.

Неиспользованный остаток AP полностью переносится между ходами. Отдельного лимита переноса нет: единственный предел — `MaxActionPoints`.

`ActionPointsPerTurn = 0` является валидным значением. В этом случае новый ход не добавляет AP, но сохраняет уже имеющийся остаток в пределах `MaxActionPoints`.

### 4. Ход завершается только явно

Достижение `0 AP` не завершает ход автоматически.

Атака, способность, предмет или перемещение также не завершают ход автоматически. Игрок может свободно чередовать действия:

```text
Move -> Attack -> Move -> Ability -> EndTurn
```

Очередь переходит к следующему участнику только через явное действие `EndTurn`.

### 5. Отдельная характеристика Movement

Существующий `MoveSpeed` переименовывается в `Movement`.

`Movement` влияет только на стоимость перемещения и не изменяет:

- инициативу;
- `StartingActionPoints`;
- `ActionPointsPerTurn`;
- `MaxActionPoints`.

Базовое нейтральное значение:

```text
Movement = 100
```

Инвариант:

```text
Movement > 0
```

`Movement <= 0` является ошибкой создания характеристик персонажа.

Возможное обездвиживание в будущем должно быть отдельным состоянием вроде `CanMove = false`, а не значением `Movement = 0`.

В MVP используется только базовое значение `Movement`. Экипировка, баффы, дебаффы и временные модификаторы мобильности не входят в первую реализацию.

### 6. Формула стоимости каждого ребра

Стоимость каждого ребра рассчитывается отдельно:

```text
stepCost = ceil(baseStepCost * 100 / Movement)
```

Где:

- `baseStepCost` равен `10` или `14`;
- `Movement > 0`;
- используется только целочисленная арифметика;
- стоимость положительного шага всегда не меньше `1 AP`;
- вычисление не должно переполнять целочисленный тип.

Однозначная безопасная реализация округления вверх:

```text
scaledCost = baseStepCost * 100

stepCost = scaledCost / Movement
         + (scaledCost % Movement == 0 ? 0 : 1)
```

Так как `baseStepCost` принимает только значения `10` и `14`, `scaledCost` не превышает `1400` и безопасно помещается в `int`.

Полная стоимость пути — сумма уже модифицированных стоимостей его рёбер:

```text
pathCost = sum(stepCost(edge))
```

Нельзя сначала построить путь по базовым `10/14`, а затем округлить или масштабировать итоговую стоимость всего пути.

`Pathfinder` обязан искать путь по фактической стоимости каждого ребра для данного `Movement`.

### 6.1. Контракт с Pathfinder

`Movement` является входным `int`-параметром каждого запроса поиска пути вместе с AP-бюджетом этого запроса.

Концептуальный контракт:

```text
FindReachable(start, actionPointBudget, movement, ...)
```

Точная сигнатура может включать дополнительные параметры карты, но обязана сохранять следующие предусловия:

```text
movement > 0
actionPointBudget >= 0
```

Оба предусловия проверяются один раз на границе запроса, до начала поиска и изменения внутренних рабочих массивов. `movement <= 0` и `actionPointBudget < 0` приводят к явному fail-fast отказу, например `ArgumentOutOfRangeException`, а не к делению на ноль или частично изменённому состоянию `Pathfinder`. Нулевой AP-бюджет является валидным штатным значением.

Контракт также обязан сохранять следующие правила:

- `Pathfinder` не хранит `Movement` как изменяемое состояние экземпляра;
- `Pathfinder` не получает объект `Hero` или `HeroStats` ради вычисления цены ребра;
- один экземпляр `Pathfinder`, принадлежащий конкретному бою, может последовательно обслуживать юнитов с разными значениями `Movement`;
- статический набор направлений хранит только базовые цены `10/14`;
- для каждого рассматриваемого ребра `Pathfinder` вычисляет фактический `stepCost` по `Movement` текущего запроса;
- фактический `stepCost` используется и при релаксации, и при отсечении по `actionPointBudget`;
- `Movement` неизменен в течение одного запроса;
- результат, рассчитанный для одного `Movement`, нельзя повторно использовать для другого `Movement` без нового поиска.

Обычный `int`-параметр выбран как минимальный и достаточный контракт. Делегаты, стратегии и интерфейсы для передачи одной числовой характеристики здесь не нужны.

### 6.2. Максимальный вес ребра и триггер пересмотра ADR-0001

После введения `Movement` фактическая максимальная стоимость одного ребра больше не является постоянной `14`.

Она зависит от минимально поддерживаемого значения `Movement`:

```text
maxEdgeWeight = ceil(14 * 100 / minimumSupportedMovement)
```

При текущем техническом инварианте:

```text
Movement > 0
Movement is int
```

теоретически минимальное значение `Movement` равно `1`, а максимальная стоимость диагонального ребра равна:

```text
ceil(14 * 100 / 1) = 1400
```

Упомянутый в ADR-0001 гипотетический размер круговых ведёр:

```text
maxEdgeWeight + 1 = 15
```

применим только к немодифицированным базовым весам `10/14`, то есть фактически к `Movement = 100`.

Для принятого `compact open-set` это не создаёт проблемы: его структура не индексируется по весу ребра.

Если триггер пересмотра ADR-0001 когда-либо сработает и будет рассматриваться переход к bucket queue, новый ADR обязан:

1. зафиксировать поддерживаемый диапазон `Movement`;
2. определить `minimumSupportedMovement`;
3. вывести из него фактический `maxEdgeWeight`;
4. только после этого определить размер кругового массива ведёр.

Константу `15` нельзя переносить в будущую реализацию bucket queue без повторного расчёта.

### 7. Одинаковая стоимость проходимой местности

Все проходимые клетки имеют одинаковый terrain-множитель.

На стоимость движения влияют только:

- направление ребра — `10` или `14`;
- `Movement` персонажа.

Элементальные и статичные поверхности, труднопроходимая местность и модификаторы стоимости клеток не входят в скоуп игры.

Специальный extension point под них в MVP не требуется.

### 8. Игрок выбирает только конечную клетку

Игрок задаёт конечную клетку, а `Pathfinder` строит канонический детерминированный маршрут.

Ручных промежуточных точек и waypoint-маршрутов нет.

До подтверждения UI показывает:

- рассчитанный путь;
- полную стоимость пути в AP;
- остаток AP после перемещения.

Preview не изменяет состояние и не расходует AP.

Результат `FindReachable` и построенный на его основе preview перестают быть валидными после любой успешной команды, изменяющей:

- `CurrentActionPoints` активного юнита;
- позицию активного юнита;
- позиции других юнитов;
- любой вход правил `CanTraverse` или `CanStopAt`.

Перед следующим preview зона досягаемости рассчитывается заново. Устаревший результат нельзя использовать для выполнения `MoveCommand`; команда обязана работать с актуальным результатом или повторно валидировать входы согласно контракту, который будет уточнён в ADR-0005.

### 9. Недоступное движение отклоняется целиком

Движение разрешено, если:

```text
pathCost <= CurrentActionPoints
```

Движение отклоняется, если:

```text
pathCost > CurrentActionPoints
```

Если конечная клетка недостижима или стоимость пути превышает текущий запас AP:

- персонаж не перемещается;
- AP не списываются;
- состояние боя не изменяется;
- UI сообщает причину, например `Недостаточно очков действия`.

Персонаж не проходит автоматически доступную часть пути и не останавливается на последней доступной клетке.

Если `pathCost == CurrentActionPoints`, движение выполняется полностью, после чего:

```text
CurrentActionPoints == 0
```

Ход при этом автоматически не заканчивается.

### 10. Движение атомарно в домене

После успешной валидации `MoveCommand` домен одной операцией:

1. списывает полную стоимость подтверждённого пути;
2. устанавливает конечную позицию персонажа;
3. возвращает или публикует рассчитанный путь для presentation-слоя.

Изменение AP и конечной позиции должно быть атомарным: невозможно списать AP без изменения позиции или изменить позицию без списания AP.

Unity-анимация визуально проигрывает уже принятое доменное решение и не управляет правилами боя.

После подтверждения движение нельзя отменить, остановить посередине или вернуть за него AP.

### 11. Нет промежуточной симуляции пути в MVP

Во время выполнения пути домен не обрабатывает:

- атаки по возможности;
- ловушки;
- эффекты пройденных клеток;
- получение урона на промежуточной клетке;
- прерывание или частичное завершение движения.

Для правил боя перемещение происходит из начальной клетки сразу в конечную.

Пройденный маршрут нужен для проверки стоимости, детерминизма и визуальной анимации.

Добавление реакций или событий на пути потребует отдельного ADR, потому что изменит атомарность `MoveCommand`, списание AP и сетевой протокол.

### 12. Атака не выполняет автоматический подход

`AttackCommand` никогда не перемещает персонажа.

Если цель находится вне дальности атаки:

- атака отклоняется;
- AP не списываются;
- позиция атакующего не меняется;
- UI сообщает, что цель вне досягаемости.

Игрок самостоятельно выбирает клетку, выполняет отдельное движение и повторяет атаку.

## Осознанно не покрыто этим ADR

Следующие вопросы должны быть решены отдельно:

- **ADR-0003 — легальность перемещения:** занятые клетки, проход через союзников и врагов, возможность остановки, точное правило диагонального угла.
- **ADR-0004 — линия видимости и укрытия:** дальность атак, LoS, касание углов, блокировка юнитами.
- **ADR-0005 — граница команд и исполнения:** конкретные DTO команд, возвращаемый результат, связь preview и execution, повторная валидация и технический механизм инвалидации зоны досягаемости после команд, изменяющих AP, позиции или правила проходимости.
- **ADR-0006 — общий контракт детерминизма:** порядок обработки команд и одинаковые результаты между средами выполнения.
- **ADR-0007 — сетевая валидация и authority:** что отправляет клиент и что повторно проверяет хост.
- **Ограничение продолжительности хода в коопе:** таймер, предупреждение, принудительный `EndTurn` и поведение при AFK. Вопрос не блокирует AP-модель, но должен быть решён до завершения сетевого этапа.

Также этим ADR не задаются конкретные балансные значения AP героев, атак, способностей и предметов.

## Отвергнутые альтернативы

| Вариант | Почему отвергнут |
|---|---|
| Отдельные AP и Movement Points | Лишает действия общей тактической валюты и усложняет состояние, UI и сетевую синхронизацию. |
| Маленькая шкала вроде 4–6 AP | Слишком грубая для движения по сетке с диагоналями и различиями мобильности; потребовала бы скрытого округления. |
| Полный сброс AP в начале хода | Убирает накопление и тактическое сохранение ресурса между ходами. |
| Автоматическое завершение хода при 0 AP | Создаёт особые случаи и не позволяет игроку осознанно завершать ход. |
| Автоматический подход при атаке | Требует поиска клетки атаки, составного действия и дополнительной сетевой валидации; не нужен для MVP. |
| Частичное движение при недостатке AP | Результат команды отличается от выбранной игроком конечной клетки. |
| Пошаговое изменение домена по клеткам анимации | Ненужная FSM- и сетевая сложность при отсутствии реакций, ловушек и поверхностей. |
| `Movement = 0` как обездвиживание | Смешивает характеристику стоимости с запретом команды и создаёт деление на ноль. |
| Поверхности и terrain-множители | Отдельный слой симуляции с влиянием на pathfinding, UI и ИИ; вырезан из текущего скоупа. |
| Хранить `Movement` внутри `Pathfinder` | Создаёт скрытое состояние между запросами разных юнитов и риск использовать неверную стоимость рёбер. |
| Сначала искать путь по `10/14`, затем масштабировать итог | Округление применяется к каждому ребру и способно изменить оптимальный маршрут; постфактум-масштабирование выбирает неверный путь. |
| Перенести константу `15` из ADR-0001 в будущую bucket queue | После введения `Movement` фактический максимальный вес ребра зависит от минимального поддерживаемого `Movement`. |

## Последствия

### Плюсы

- Одна понятная валюта для всех действий.
- Целочисленная и детерминированная стоимость движения.
- Накопление AP создаёт тактический выбор без второй системы ресурсов.
- `Pathfinder` сразу ищет путь по реальной цене для конкретного героя.
- Неуспешные команды не изменяют состояние.
- Атомарное движение удобно тестировать и в будущем валидировать на хосте.
- Анимация отделена от доменной логики.
- MVP не зависит от поверхностей, реакций и составных команд.

### Минусы, принятые осознанно

- Игроку приходится самостоятельно искать клетку для атаки по цели вне радиуса.
- Нельзя вручную задать обходной маршрут через промежуточные точки.
- Нельзя остановить уже подтверждённое движение.
- В MVP путь не может быть прерван событием на промежуточной клетке.
- Высокоточная шкала AP требует отображать большие целые значения либо форматировать их в presentation-слое.
- Запрос `Pathfinder` зависит от `Movement` конкретного юнита, поэтому результат нельзя кэшировать без включения `Movement` в ключ кэша.
- Потенциальный будущий переход к bucket queue потребует сначала зафиксировать диапазон `Movement`.

## Минимальный набор подтверждающих тестов

### HeroStats / Hero

- `CurrentActionPoints` в начале боя равны `StartingActionPoints`.
- Первый ход не получает дополнительное `ActionPointsPerTurn`.
- Начало последующего хода добавляет `ActionPointsPerTurn`.
- AP ограничиваются `MaxActionPoints`.
- Неиспользованный остаток переносится.
- Успешная трата уменьшает AP на точную величину.
- Неуспешная трата не изменяет AP.
- `Movement <= 0` отклоняется.
- `ActionPointsPerTurn = 0` является валидным: начало нового хода не выбрасывает исключение и не изменяет текущий остаток AP.

### Movement cost

- При `Movement = 100` шаги стоят `10` и `14`.
- При `Movement < 100` стоимость увеличивается с округлением вверх.
- При `Movement > 100` стоимость уменьшается с округлением вверх.
- Положительный шаг никогда не стоит `0 AP`.
- Полная стоимость пути равна сумме модифицированных стоимостей рёбер.
- Целочисленная реализация через `/` и `%` корректна при `Movement` значительно больше `scaledCost` и возвращает минимум `1`.

### Валидация входов Pathfinder

- `movement = 0` отклоняется до начала поиска.
- `movement < 0` отклоняется до начала поиска.
- `actionPointBudget < 0` отклоняется до начала поиска.
- При отказе внутренние рабочие массивы и публичный результат не изменяются частично.
- `actionPointBudget = 0` является валидным: при `movement = 100` и `CanStopAt(start) = true` достижима только стартовая клетка со стоимостью `0`; ни одно положительное ребро не входит в результат.

### Интеграция Movement с Pathfinder

Тестовая карта через контролируемый `CanTraverse` оставляет ровно два маршрута из `(0, 0)` в `(10, 0)`.

Первый маршрут содержит четырнадцать ортогональных рёбер:

```text
(0,0) -> (0,1) -> (0,2) -> (1,2) -> ... -> (10,2) -> (10,1) -> (10,0)
```

Второй маршрут содержит десять диагональных рёбер:

```text
(0,0) -> (1,1) -> (2,0) -> (3,1) -> ... -> (9,1) -> (10,0)
```

При базовых весах оба маршрута стоят:

```text
14 * 10 = 10 * 14 = 140
```

Пара `14/10` является минимальной для чисто ортогонального и чисто диагонального маршрутов к одной цели.

Меньшее арифметическое равенство:

```text
7 * 10 = 5 * 14 = 70
```

нельзя реализовать такими двумя маршрутами к одной конечной клетке: семь ортогональных шагов меняют чётность `x + y`, а любое количество диагональных шагов её сохраняет.

При `Movement = 60`:

```text
orthogonalStep = 17
fourteenOrthogonalEdges = 238

diagonalStep = 24
tenDiagonalEdges = 240
```

`Pathfinder` обязан выбрать ортогональный маршрут стоимостью `238`.

При `Movement = 80`:

```text
orthogonalStep = 13
fourteenOrthogonalEdges = 182

diagonalStep = 18
tenDiagonalEdges = 180
```

`Pathfinder` обязан выбрать диагональный маршрут стоимостью `180`.

Тест должен задавать ожидаемые маршруты и стоимости независимо от вывода проверяемой реализации.

Нельзя сначала запустить новый `Pathfinder` и сохранить его первый результат как oracle характеризационного теста.

Повторный запрос с другим `Movement` обязан выполнить новый поиск и не переиспользовать путь предыдущего запроса.

При `Movement = 100` оба маршрута стоят `140`. Этот случай подтверждает совпадение базовой и фактической шкалы и то, что равная последующая релаксация не переписывает уже установленного предшественника. Он не заменяет отдельный тест выбора минимума из `openList`.

### Детерминированный выбор минимума и строгая релаксация

Выбор следующей клетки из compact open-set проверяется отдельно от геометрии и порядка таблицы направлений. При равной стоимости всегда выбирается меньший `cellIndex`, независимо от порядка элементов `openList`:

```text
cost[5] = 20
cost[9] = 20

openList = [9, 5] -> выбирается 5
openList = [5, 9] -> выбирается 5
```

Дополнительный случай после перестановок, характерных для `swap-remove`:

```text
openList = [17, 9, 5]
cost[17] > 20
cost[9] = 20
cost[5] = 20

выбирается 5
```

Тест обязан падать при реализации «первый вставленный побеждает», «первый элемент массива побеждает» или использовании текущей позиции после `swap-remove` как тай-брейка. Внутренняя операция выбора может быть доступна тестовой сборке через `internal` и `InternalsVisibleTo`, не становясь публичным API.

Интеграционный diamond-тест использует контролируемый граф:

```text
start = (1,1)
left  = (0,2)
right = (2,2)
goal  = (1,3)
```

Разрешены только рёбра `start <-> left`, `start <-> right`, `left <-> goal`, `right <-> goal`; все они диагональные и при `Movement = 100` стоят `14`. При `cellIndex(left) < cellIndex(right)` ожидаемый канонический путь — `start -> left -> goal`, а равная релаксация через `right` не переписывает предшественника цели. Diamond-тест проверяет интеграционное следствие, а перестановочно-инвариантный unit-тест выше — сам тай-брейк независимо от порядка направлений.

### Граница AP для движения

Этот тест не переиспользует большую карту из предыдущего интеграционного теста.

Используется отдельная маленькая конфигурация:

```text
Movement = 100
путь = 2 ортогональных ребра
pathCost = 20
```

При:

```text
CurrentActionPoints = 20
```

ожидается:

- движение разрешено;
- позиция изменена;
- `CurrentActionPoints == 0`;
- ход автоматически не завершён.

Соседний отрицательный тест:

```text
CurrentActionPoints = 19
pathCost = 20
```

ожидает:

- движение отклонено;
- позиция не изменена;
- `CurrentActionPoints` остались равны `19`;
- ход автоматически не переключён.

### Turn flow

- `0 AP` не переключает ход автоматически.
- Обычное действие не переключает ход автоматически.
- Только успешный `EndTurn` передаёт очередь следующему участнику.

### Move execution после ADR-0003

- Недоступное или слишком дорогое движение не меняет AP и позицию.
- Успешное движение одновременно списывает полную стоимость и меняет конечную позицию.
- Несколько `MoveCommand` можно выполнить в одном ходу при достаточном запасе AP.

## Синхронизация документации

При принятии ADR необходимо синхронно обновить `docs/domain_model.md`:

- переименовать `MoveSpeed` в `Movement`;
- заменить описание «сколько клеток проходится за 1 AP» на описание характеристики, модифицирующей стоимость каждого ребра;
- добавить `StartingActionPoints` и `ActionPointsPerTurn`;
- уточнить, что `MaxActionPoints` — верхняя граница накопленного AP, а не «очки за ход»;
- сохранить `CurrentActionPoints` как изменяемое состояние `Hero`, а не `HeroStats`;
- честно отметить, если архитектурное решение уже принято, но код ещё не реализован.

## История пересмотра

- Первый черновик зафиксировал единую AP-экономику, накопление AP, `Movement`, атомарное движение и отказ от поверхностей и промежуточных событий.
- Внешнее ревью выявило недоспецифицированную границу между ADR-0001 и ADR-0002: в черновик добавлен явный `Movement`-параметр каждого запроса `Pathfinder`.
- Добавлен независимый интеграционный тест, в котором изменение `Movement` меняет оптимальный маршрут из-за округления стоимости каждого ребра.
- Добавлены границные тесты `pathCost == CurrentActionPoints` и `ActionPointsPerTurn = 0`.
- Формула округления переписана через целочисленные `/` и `%`, чтобы исключить переполнение при неограниченном сверху `Movement`.
- В список затронутых файлов добавлен `docs/domain_model.md`.
- Политика таймера и AFK в коопе явно отложена.
- Повторное ревью выявило, что константа `maxEdgeWeight + 1 = 15` из гипотетического bucket-queue-триггера ADR-0001 больше не универсальна после введения `Movement`.
- Уточнено, почему тестовая пара `14` ортогональных и `10` диагональных рёбер является минимальной геометрически возможной.
- Границный тест AP вынесен в отдельную маленькую конфигурацию, независимую от интеграционного теста выбора маршрута.
- Финальное ревью добавило инвалидацию зоны досягаемости после изменения AP, позиций или правил проходимости.
- Контракт `Pathfinder` дополнен fail-fast предусловиями `movement > 0` и `actionPointBudget >= 0`; нулевой бюджет зафиксирован как валидный случай.
- Проверка тай-брейка разделена на перестановочно-инвариантный unit-тест выбора минимума и diamond-интеграцию строгой релаксации.

## Правило изменения решения

После принятия этот ADR не редактируется для изменения механики.

Любое последующее изменение общей AP-экономики, формулы `Movement`, атомарности движения, инвалидации зоны или поведения при недостатке AP оформляется новым ADR, который явно заменяет ADR-0002.
